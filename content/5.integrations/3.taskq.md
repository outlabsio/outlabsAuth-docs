Use **Outlabs Auth** for identity and permission checks, **Auth UI** to
administer that identity system, and **TaskQ** to execute durable jobs. Each
component has its own role and can be adopted separately.

| Component | Runs where | Owns | Start here |
| --- | --- | --- | --- |
| Outlabs Auth | Inside your FastAPI host | Users, sessions, roles, permissions and API keys | [Auth quickstart](/getting-started/getting-started) |
| Auth UI | Separate static website | Screens for managing the host's Auth APIs | [Console setup](/integrations/outlabsauth-ui) |
| TaskQ | PostgreSQL plus API/worker/scheduler processes | Enqueue, claim, retry, settle and schedule jobs | [TaskQ quickstart](https://taskq.outlabs.io/getting-started/quickstart/) |

```text [deployment]
Browser -> Auth UI -> FastAPI host
                      |-- /v1/auth, /v1/users, /v1/roles, ... -> Outlabs Auth
                      |-- /taskq/v1/... -> TaskQ facade + OutlabsQueueAuthorizer
                                          |-- Auth authenticates and checks permissions
                                          |-- TaskQ SQL owns job state
HTTP workers ----------------------------> /taskq/v1/...
One scheduler ---------------------------> TaskQ PostgreSQL
```

Auth and TaskQ may share a PostgreSQL server or use separate databases. The
console talks to the Auth API; HTTP workers talk to the TaskQ facade. The
scheduler and facade's SQL transports need their own database access.

::note
Auth UI manages identities, role grants and credentials. It does not list TaskQ
jobs, operate queues or start workers and schedulers. Use the
[TaskQ CLI](https://taskq.outlabs.io/getting-started/cli/) for those operations.
::

## 1. Start with Auth

Complete the [Auth quickstart](/getting-started/getting-started), then mount
the management routers needed by the console. Match the console's
`apiBaseUrl`, `authApiPrefix` and optional `frontendProfileKey` to that host.
For `/v1/auth`, use `authApiPrefix: "/v1"`.

The examples below target published Auth **0.1.0a37** and TaskQ **0.1.0a42**:

```bash [Terminal]
pip install "outlabs-taskq[outlabs]==0.1.0a42" "outlabs-auth==0.1.0a37"
```

The TaskQ `[outlabs]` extra installs the HTTP/Auth adapter. Auth alone does not
install TaskQ, and TaskQ can use direct SQL or other HTTP authorizers without
Outlabs Auth. The console is installed and deployed separately.

## 2. Add the TaskQ facade

Follow [TaskQ's Auth integration guide](https://taskq.outlabs.io/getting-started/auth-and-admin-ui/)
for the mount function, Auth session provider, permission provisioning and
worker context. That guide connects `OutlabsQueueAuthorizer` to your host's
Auth instance and mounts `create_taskq_app` under `/taskq`.

The API prefixes are independent: the console's `/v1` does not configure the
TaskQ client's `/taskq/v1/...` paths. Keep Auth initialization, TaskQ SQL
transports and resource cleanup in the host lifespan. A facade mount alone
starts neither workers nor scheduling.

## 3. Grant access in the right layer

| Layer | Configure it with | What it controls |
| --- | --- | --- |
| Auth identity and policy | Auth UI, Auth CLI, or host-owned IAM setup | Who can authenticate and which TaskQ permission names they hold |
| TaskQ HTTP actions | `OutlabsQueueAuthorizer` | Whether that principal may enqueue, run, read, control or administer a queue |
| TaskQ database capabilities | PostgreSQL roles and queue admission ownership | Which database LOGIN can call SQL operations and admit work |

Console access alone does not establish a worker credential or SQL queue
ownership. Auth superusers and broad grants can authorize more than a dedicated
worker needs. Provision TaskQ's permission catalog, grant only the needed actions,
and test both allowed and denied requests on the actual host. Avoid broad
global permissions when a worker should access only one queue.

The console's Users, Roles, Permissions and Service accounts workspaces help
manage the corresponding Auth records when the host exposes them. TaskQ's CLI
inspects jobs and controls queues. Creating an Auth permission does not create
a TaskQ queue, bind its SQL producer owner or start a worker.

## 4. Run workers and scheduling

Use a dedicated worker credential supplied by the host's secret manager or
supervisor. Keep token/key issuance, expiry and rotation with Auth and the host;
TaskQ consumes the configured credential. A signed-in console session is not a
worker credential. See the [worker context example](https://taskq.outlabs.io/getting-started/auth-and-admin-ui/#connect-an-http-worker).

Run one supervised scheduler for recurring jobs and a separate supervised
worker fleet. Queue state, concurrency and provider/spend limits remain
application choices. Begin with a bounded canary before enabling recurring
work.

## Optional: run Auth maintenance through TaskQ

The reverse direction is also useful: TaskQ can schedule Auth's cleanup and
usage-sync work. Keep `background_job_mode="disabled"` in API replicas, register
a host task that calls `auth.run_maintenance_once()`, and translate a false
`report.ok` into a retry outcome. The worker executing that task needs access
to Auth's database and configured Redis even if it receives jobs over HTTP.

Use [Background Maintenance](/getting-started/background-maintenance#optional-taskq-pattern)
for the host-owned task and paused schedule pattern, and the
[TaskQ standalone scheduler](https://taskq.outlabs.io/operations/standalone-scheduler/)
for the clock and manifest setup.

## Verify the combined application

- Log in through Auth UI and confirm its discovered surfaces and frontend profile.
- Grant a test identity only its required queue actions. Confirm an allowed
  request succeeds and an attempt to run work on an unrelated queue is refused.
- Enqueue one deterministic-key job; observe its worker and terminal result
  through the TaskQ CLI.
- If scheduling Auth maintenance, require one complete successful report and
  prove API replicas do not run a second maintenance loop.

Package upgrades, database migrations and console deployments are separate
steps. See [Auth versions and upgrades](/getting-started/versions-and-upgrades)
and [TaskQ runtime-first upgrades](https://taskq.outlabs.io/operations/runtime-first-upgrades/).
